designc and factory-s2: getting started

designc (System 1) is the desktop app where you design. factory-s2 (System 2) is the pipeline that turns a frozen design into merged code. They share files, not a server: the design folder (also called the registry) and its ledger.

The design folder holds the model, requirements, decisions and ledger as plain files. It can sit inside your code repo (for example design/) or beside it, and a new empty folder is fine.

The idea

The design is the source of truth and code is a build output. Models propose; deterministic checks and people decide. An agent never writes anything without a policy check, and writes need a person's approval.

designc (you design)  ──freeze──►  handover  ──►  factory-s2 (plans, builds, verifies, merges)
        ▲                                                         │
        └──────────── ledger (append-only events) ◄───────────────┘

First 10 minutes

No model, key or cost needed.

When you want a model, a reviewer or Langfuse, run scripts/setup-wizard.sh: a step-by-step prompt that writes ~/.config/factory-s2/env (mode 600, outside the repo). Connection tests are free and only run if you say yes.

  1. npm install && npm start, then choose Try the sample project. The first launch also shows a short tour (Help, Take the tour, shows it again). This opens sample-registry/, a small pricing-engine design.
  2. Look at the status bar: the gate says not ready. In the Design sidebar, the blocking clauses are listed in the order to work them. The first one is marked next.
  3. Open model/workspace.dsl from the Explorer. Findings (DC000 to DC009) appear in the Problems panel as you read; click one to jump to the line.
  4. On a finding, try Ask the tutor to have it explained, or Record decision to write down how you will resolve it. Nothing is bound until you press Bind.
  5. Switch to Build and Improve to see what the sample ledger looks like once a pipeline has run.
  6. To see the other half, run the model-free factory-s2 commands in "Running factory-s2" below. They print the plan and the waves of tasks without calling anything.

The sample is copied from the repo; changes you make are written to the folder, so work on a copy if you want to keep it clean.

Terms

TermWhat it is for
RegistryThe folder that holds one design: model, decisions, requirements, scenarios, handovers and the ledger. Plain files, kept in git.
ModelThe Structurizr DSL file (model/workspace.dsl) with d.* properties that state design intent such as interaction type or code areas.
FindingA lint result from the design compiler. It says what looks wrong or unknown in the design.
DecisionA recorded answer to a finding or a requirement. It moves from minted to checked to bound; only a person binds.
GateThe yes/no answer to "is this design ready to build?". It lists every clause still blocking.
HandoverA frozen, never rewritten copy of the design that a pipeline builds from, including elements.json and a BUILD.md brief.
Work itemA slice of a requirement tied to some elements. It is Done only with a passing gate at a commit on main.
LedgerAppend-only event log shared by designc and the pipeline. It is how they talk without a server.
Code map and driftThe as-built model extracted from code, compared with the design to show what differs.
EscapeA defect that got through; Improve records which stage should have caught it.

Using designc

Install and open

npm install
npm start                          # opens the app
npm start -- /path/to/registry     # opens straight into a registry folder

Needs Node 20 or later. Use Try the sample project to explore sample-registry/, a small pricing-engine design with a decision, a requirement, and a sample ledger. A registry is a plain folder, so git gives you review and history.

The views

ViewUse it to
DesignEdit the Structurizr model with d.* properties, see live findings (DC000 to DC009), the C4 sheet, decisions, requirements, and the gate.
Code mapExtract a .NET or JS/TS codebase into a C4 model and see drift against your design.

Agent panelChat with Architect, Grill-me, Analyst or Tutor on the built-in model, any ACP agent, or an AG-UI service.

A first pass

  1. Open your design folder (File, Open Design Folder). The status bar shows the gate: ready or not, with each blocking clause listed in the Design sidebar in working order.
  2. Work the clauses. A finding offers Record decision or Accept risk; an unbound decision offers Bind; a decision check offers Run check. Binding is always a person's action.
  3. When the gate is ready and your files are committed, Freeze handover. It writes handovers/<id>/ with copies of the model, requirements, bound decisions, scenarios, evals, an elements.json and a BUILD.md brief. A frozen handover is never rewritten.
  4. Dispatch it: set dispatch in designc.json to your pipeline command. designc types the filled command into the integrated terminal and stops before Enter.

Settings

designc.json in the registry holds settings, and only the names of environment variables for secrets. The Set up page (opened when a folder has no designc.json) walks through the model, LLM and Langfuse sections, each skippable, with a Test connection button.

{
  "model": "model/workspace.dsl",
  "codebase": "../pricing-repo",
  "dispatch": { "pipeline": { "label": "Build it",
    "command": "my-build --handover {handover} --repo {repo} --registry {registry} --base {base}" } }
}

CI

cd python && python3 -m designc check <registry>    # exit 0 ready, 1 not ready, 2 unreadable folder

Running factory-s2

Try it without a model

dotnet run --project tests/Factory.Core.Tests
dotnet run --project src/Factory.S2 -- validate --handover examples/pricing-v3/handover.json --plan examples/pricing-v3/plan.json
dotnet run --project src/Factory.S2 -- dispatch --handover examples/pricing-v3/handover.json --plan examples/pricing-v3/plan.json

validate and dispatch are deterministic: no agents, no network, no cost. dispatch prints the waves of tasks that can run in parallel.

A real run

This calls a paid model. Pick one provider setup.

# an LLM gateway
export FACTORY_GATEWAY_URL=https://<gateway>/v1 FACTORY_GATEWAY_KEY=<key>
export FACTORY_MODEL_FRONTIER=<alias> FACTORY_MODEL_STANDARD=<alias> FACTORY_MODEL_SMALL=<alias>
# or the Anthropic API
export FACTORY_PROVIDER=anthropic ANTHROPIC_API_KEY=<key>

dotnet run --project src/Factory.S2 -- run \
  --handover <registry>/handovers/<id>/handover.json \
  --repo <target repo> --registry <registry> [--base main] [--github]

The reviewer and QA must run on a different model family from the author. Start-up refuses otherwise; with one provider only, FACTORY_REVIEWER_SAME_FAMILY=allow allows dry-run merges and stamps the reviews as same-family. Without --github, pull requests are written under .factory/runs/<id>/ instead of opened.

Agent contracts

If the design has agents, designc can compile a contract for each (Design sidebar, Agent contracts) and copy the compiled files into the handover at freeze. S2 reads them: FACTORY_CONTRACTS=warn (the default) names agents that have none, require refuses to start a run, off ignores them. S2 does not yet enforce the policy while a run is going; that is still to do.

Useful commands

CommandWhat it does
run --run-id <id>Resume a run.
run --repair <run>Repair a run that ended integration_failed.
budget --repo . --registry rCheck spend caps. Exit 2 when exceeded; run then exits 4.
digest --registry rWhat needs you, what failed, what finished.
pull-plan, metricsRead-only reports over the registry.
qa --repo . --run-id <id>Follow-up QA without an author.

Every run leaves .factory/runs/<id>/result.json saying how it ended (merged, parked, failed, integration_failed, refused, and so on).

Start with tight limits and loosen them as the numbers justify it. Per-repo policy lives in .factory/ files (integration, merge, quality, npm, UI contract); see the factory-s2 README and ARCHITECTURE.md.

The whole loop

  1. In designc, work the gate to ready and commit the registry.
  2. Freeze a handover (whole model, or one work item for a scoped slice).
  3. Dispatch it to factory-s2 with run.
  4. If the pipeline needs a human answer, it writes a needs_decision to the ledger. Open Build or the Work digest in designc and answer with a decision.
  5. When the pipeline merges, check evidence in Build. A work item is Done only with a passing gate at a commit on main; an agent's claim is never enough.
  6. Extract the code map to see drift, and use Improve to classify escapes.

What is guarded

  • Agents cannot bind decisions, freeze handovers, or write the ledger's human-only events.
  • Registry access is confined to the open folder; child processes do not inherit secrets.
  • The ledger is append-only and validated on every write.
  • Checks, git and the terminal run only in a folder you have trusted.
